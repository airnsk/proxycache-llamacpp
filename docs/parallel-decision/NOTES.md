# Decision engine (Jev / `parallel-decision`) — our notes

Что это и как устроено, что мы добавили и какие у этого границы. Все числа ниже — наши замеры
на стенде ai-370 (Radeon 890M, Vulkan/RADV, модель Qwen3.8-Flash-Next UD-IQ4_XS).

## Что это

- Ветка-донор: `thecodacus/llama.cpp`, ветка `parallel-decision` (эндпоинт `/v1/decision`, тул
  `llama-parallel-decision`, движок `tools/parallel-decision/decision-engine.{h,cpp}`).
- У нас: влита в ветку `decision-parallel` (свежий upstream + наш дисковый кэш + Jev + демо-UI).
- Идея: не генерировать JSON токен за токеном, а **отскорить все допустимые значения полей схемы
  за один батчевый проход**, вернуть значение + вероятность по каждому полю; JSON собирает код,
  поэтому ответ всегда валиден по схеме.

### Эндпоинты и флаги

| что | как |
| --- | --- |
| решение | `POST /v1/decision` (алиас `POST /decision`) |
| включить | `--decision-seqs N` (N ≥ 3); без него эндпоинт выключен |
| демо-UI | `GET /decision/` — `--decision-webui` (по умолчанию **включён**), выключается `--no-decision-webui` |
| CLI | `llama-parallel-decision MODEL N_CPU_MOE --worker N_CTX N_BATCH` (воркер: запросы строками со stdin) |

### Тело запроса (кратко)

- `instructions` — статический префикс (кэшируется вместе с каталогом полей);
- `schema` — поля: `enum` (`choices`, 1..255), `boolean`, `integer` (`minimum`/`maximum`),
  `number` (`minimum`/`maximum`/`step`, `aggregate`: mode|median|mean);
  **`description` обязателен у каждого поля** (иначе 400);
- `contexts` — 1..256 задач, все делят один префикс, ответ в том же порядке;
- `mode` (`auto`|`tree`|`greedy`), `tree_max` (128), `cache_prompt` (true).

В ответе: `results[].decision` (готовый JSON), `results[].fields{value,probability,scored_nodes,tree}`,
`usage{prompt_tokens,cached_tokens,context_tokens,scored_rows}`, `timings{prefill_ms,scoring_ms,total_ms,rounds,per_decsion_ms}`.

## `--decision-seqs` — что это на самом деле

Это **N KV-последовательностей сверх обычных слотов сервера** (`n_seq_max = n_parallel + N`),
зарезервированных под движок:

1. `seq_snap` — одна последовательность держит **кэшированный статический префикс** (instructions + каталог полей);
2. ствол — первая из пула: контекст задачи, от него форкаются ветки;
3. ветки — остальные последовательности пула: по одному кандидатному значению на ветку.

Почему минимум 3 — авторская формулировка из кода: `needs at least 3 (cached prefix, trunk, one branch)`.
Флаг заодно переводит KV в `unified`, иначе ветки не могут делить ячейки префикса.
N — это ёмкость параллельного скоринга: хватает слотов → `rounds = 1`, не хватает → движок
разбивает работу на несколько проходов (`rounds > 1`).

## Границы, которые важно знать

- **Один префикс на движок.** В движке единственный список `cached` и единственный `seq_snap`
  (`decision-engine.h`), поэтому при смене префикса он сносит свои последовательности и считает
  новый префикс заново. Место в KV тут ни при чём — это упрощение реализации.
  Цена смены (наши замеры): 172 токена → 3,3 с; 16,4k токенов → 196 с.
  Работает это для «много задач с одним префиксом»: они попадают в кэш сами, группировать не нужно
  (две отдельные HTTP-задачи: вторая дала `cached_tokens = 151` при холодных 0).
- **Слоты не участвуют.** Решение приходит отдельной задачей и работает в собственных
  последовательностях, поэтому слотовый prompt-cache и его зеркала (наш дисковый уровень) по
  умолчанию его не видят.
- **Дедупликации между слотом и движком нет.** Если один и тот же текст лежит и в слоте, и в
  `seq_snap`, это две последовательности и две копии ячеек: unified-кэш делит ячейки только при
  явном `seq_cp`, «само» не схлопывается. Мульти-префиксность (таблица префиксов + LRU) не сделана.

## Что добавили мы

1. **Персист префикса решений через наш дисковый кэш** (`--cache-disk`):
   - в движке — необязательный хук `llama_decision::prefix_store` (`load`/`save`); при `store == nullptr`
     поведение прежнее (только память);
   - на стороне сервера — адаптер `decision_prefix_store` над `server_disk_cache`:
     `find(tokens)` → `load(ctx_tgt, seq_snap, id)` при попадании, `save(ctx_tgt, seq_snap, tokens)`
     после холодного префилла;
   - итог: снапшот префикса становится обычной записью состояния в нашем namespace — с тем же
     вытеснением, тем же отпечатком модели и персистом через перезапуск сервера.
2. **RAM prompt-cache остаётся на дефолте 8192 МиБ и при включённом `--cache-disk`**
   (раньше при диске по умолчанию поднимался до 32 ГиБ; убрано).
3. Для решений `--cache-disk-min-tokens` должен быть **ниже длины префикса** (у нас префикс ~172
   токена → запускаем с `--cache-disk-min-tokens 64`, иначе на диск не пишется ничего).
